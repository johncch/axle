# Migrating to Axle 0.35.0

0.35.0 fixes how a configuration mistake reaches the caller. A result's
`ok: false` now carries one thing only, the provider's answer to a request
that went out, and everything else throws a coded `AxleError` before any
request is sent. The failure type is renamed `AxleProviderFailure`, its
`model` kind is split into `api` and `incomplete`, every thrown error has a
`code` from the new `AxleErrorCode`, and `isAxleError` narrows a catch.
`InstructVariableError` is renamed and `TaskError` is removed.

0.35.0 also adds continuations: a send can carry `after`, a program that
runs once the turn has settled, holds the queue until it returns, and runs
further turns inline. `AgentResult` and `AgentErrorResult` gain `after`,
and `onSettled` now fires after every turn that commits, which is once per
send unless the send carries a continuation.

The Axle CLI is a separate product; its changes are recorded in
[packages/axle-cli/CHANGELOG.md](../packages/axle-cli/CHANGELOG.md).

---

## Breaking changes

### `AxleFailure` is `AxleProviderFailure`, and `model` is two kinds

The `ok: false` arm's `error` is typed `AxleProviderFailure`. The old name
and the `GenerateError` alias are gone. Its `kind` was
`model | refusal | parse`; it is now `api | incomplete | refusal | parse`,
cut on what the API did:

| Kind         | What the API did                                                                   | `status`                   | `usage`                       |
| ------------ | ---------------------------------------------------------------------------------- | -------------------------- | ----------------------------- |
| `api`        | Did not complete the request: rejected it, failed mid-way, or the connection broke | present when there was one | usually absent                |
| `incomplete` | Completed the request and stopped for a reason that is not a usable end            | absent                     | present; the call was charged |
| `refusal`    | Completed the request by declining it or blocking its output                       | absent                     | present                       |
| `parse`      | Completed the request; the answer is outside the Instruct's schema                 | absent                     | present                       |

`api` carries what `model` carried: `type`, `message`, `status?`, `usage?`,
`raw?`. `incomplete` carries `type`, `message`, `usage?`, `raw?`, where
`type` is the stop reason verbatim or one of `FinishReasonError`,
`IncompleteStream`, `RESPONSES_API_INCOMPLETE`. Those three used to arrive
as `kind: "model"`.

```ts
// Before
if (!result.ok && result.error.kind === "model") retryOrFix(result.error);

// 0.35
if (!result.ok) {
  switch (result.error.kind) {
    case "api": // fix on 4xx, back off on 429 / 5xx
    case "incomplete": // retry the same request
    case "refusal":
    case "parse":
  }
}
```

A `switch` on `kind` that ends in an exhaustiveness check stops compiling
until it handles `api` and `incomplete`.

### Setup mistakes reject instead of resolving `ok: false`

A request Axle could not build used to be caught by the adapter's own try
and resolved `ok: false` with `kind: "model"`, `type: "Error"`, and no
`status`, labelled the same as a 500 from the API although nothing was
sent. These now throw an `AxleError` before any request:

| Mistake                                                                                                                                                                                                                                                                    | Code                   | `details`               |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ----------------------- |
| A loop limit below 1; a non-integer `maxRetries` or `timeoutMs`; a bad model id; an unsupported reasoning setting; a tool choice naming an absent tool; a tool schema Zod cannot express as JSON Schema; a Brave option out of range                                       | `INVALID_OPTIONS`      | none                    |
| A feature this provider has no wire shape for: a non-PDF document, an unsupported image type, a content source with no block type, Gemini `parallelToolCalls: false` or provider tool choice, a Chat Completions provider tool with nothing to serve it, a PDF on Together | `PROVIDER_UNSUPPORTED` | `{ provider, feature }` |
| A host file that could not be resolved: not found, too large, unsupported type, wrong category, no `fileResolver`                                                                                                                                                          | `FILE_UNREADABLE`      | `{ path? , name? }`     |
| An MCP tool called before `connect()`                                                                                                                                                                                                                                      | `MCP_NOT_CONNECTED`    | none                    |

A host that checked `result.ok` and then fixed its configuration from the
message now does that in a `catch`. A bad API key is not in the table: the
request goes out and the provider's 401 comes back as `api` with
`type: "authentication"`, as before.

```ts
// Before
const result = await generate({
  provider,
  model,
  messages,
  toolChoice: { type: "tool", name: "nope" },
});
if (!result.ok && result.error.type === "Error") fixSetup(result.error.message);

// 0.35
try {
  const result = await generate({
    provider,
    model,
    messages,
    toolChoice: { type: "tool", name: "nope" },
  });
} catch (error) {
  if (isAxleError(error) && error.code === "INVALID_OPTIONS") fixSetup(error.message);
}
```

An invalid reasoning setting threw a `TypeError`; it throws
`AxleError` `INVALID_OPTIONS`.

### Tool arguments that do not parse are a tool error, not a throw

On Anthropic and OpenAI, a tool call whose arguments were not valid JSON
made the handle reject with a plain `Error`. It is now an
`invalid-arguments` tool error fed back to the model, as Chat Completions
already did, and the loop goes on.

### Two stop reasons change

A Chat Completions `finish_reason` outside `stop`, `eos`, `length`,
`tool_calls` and `function_call` used to be reported as `Stop` with
`ok: true`. It is `ok: false`, `kind: "incomplete"`,
`type: "FinishReasonError"`, like the other three adapters. Gemini's
`LANGUAGE` finish reason was an unmapped stop; it is a `refusal` with
`category: "LANGUAGE"`.

### `InstructVariableError` is `AxleInstructVariableError`; `TaskError` is gone

```ts
// Before
import { InstructVariableError } from "@fifthrevision/axle";
if (error instanceof InstructVariableError) ...

// 0.35
import { AxleInstructVariableError } from "@fifthrevision/axle";
if (error instanceof AxleInstructVariableError) ...
```

`TaskError` was exported and never thrown.

### `AxleError.code` and `details` are typed

`code` is `AxleErrorCode`, a union of string literals, so a `code` option
outside the set no longer compiles. `details` is
`Record<string, unknown>` instead of `Record<string, any>`; a read of
`error.details?.status` that did arithmetic on it needs a `typeof` check.
The payload classes no longer set `details`: `AxleAbortError`,
`AxleToolFatalError` and `AxleInstructVariableError` carry `reason`,
`toolName`, `usage` and `missingVariables` as fields only, and their
`toJSON` output loses the duplicated `details` object.

### A provider throw closes spans

When the provider's generator threw, the step span and the run span were
left open. Both now end with `"error"` before the handle rejects.

## Additions

### `AxleErrorCode` and `isAxleError`

```ts
import { AxleErrorCode, isAxleError } from "@fifthrevision/axle";

try {
  await agent.send(instruct).final;
} catch (error) {
  if (!isAxleError(error)) throw error;
  switch (error.code) {
    case AxleErrorCode.ABORTED: // error is AxleAbortError | AxleAgentAbortError
    case AxleErrorCode.TOOL_FATAL_ERROR: // error is AxleToolFatalError
    case AxleErrorCode.INSTRUCT_VARIABLE_ERROR: // error is AxleInstructVariableError
    case AxleErrorCode.PROVIDER_UNSUPPORTED: // error.details.provider, error.details.feature
  }
}
```

`isAxleError` narrows to `AnyAxleError`, the union of the payload classes
and the base, and the classes declare their `code` as a literal so the
`switch` narrows to the class. The guard tests for an `Error` carrying an
`AxleErrorCode`, not `instanceof`, so it holds when a host has two copies
of the package. Prefer it over `instanceof AxleError`. The full table of
codes is in `docs/architecture/errors.md`.

### `after` on `send()`

```ts
const handle = agent.send("Summarize the report.", {
  after: async (result, ctx) => {
    for (let attempt = 0; attempt < 3; attempt++) {
      const verdict = await judge(result);
      if (verdict.ok) break;
      result = await ctx.send(verdict.feedback);
    }
  },
});
agent.send("Next question."); // waits until the continuation returns
```

The continuation runs after the send's turn settles with a result, `ok` or
not; a turn whose handle rejects (cancelled, a fatal tool error, a setup
failure) skips it. It holds the queue until it returns. `ctx.send()` runs
an inline turn: the same arguments as `send()` without `after`, an ordinary
turn in every way except that it starts at once with no `pending:queued`,
resolved with the turn's result after that turn's `onSettled` has
resolved. Inline sends run one at a time in call order and return a
promise, not a handle. `ctx` also carries `signal`, `id` (the send's user
turn id), and read-only `messages` and `pending`.

`cancel()` during a continuation aborts `ctx.signal` and any inline turn in
flight and rejects the handle; before it starts, it never starts. `stop()`
keeps its tool-batch meaning for an inline turn in flight. `clear()` never
touches a continuation. A continuation that throws rejects the handle and
the queue continues. A manual `compact()` carries no continuation, and an
inline turn carries none.

`Continuation`, `ContinuationContext`, `InlineSendOptions` and `InlineTurn`
are exported.

### `after` on results

The handle resolves when the continuation returns, with the inline turns
listed in order under `result.after`, each an `InlineTurn`: the `userTurn`
it sent and its own `ok`, `response`, `turn` and `usage`. The top-level
fields stay the message you sent and its reply; a caller wanting the
corrected answer reads the last entry. Inline responses are typed
`unknown`, since only the continuation saw the inline send's schema. The
field is present only when the send carried a continuation; a plain send's
result has no `after`.

## Behavior changes

### `onSettled` fires per committed turn

It used to fire once per operation. It now fires after every turn that
commits and once for an operation that ran without opening a turn. For a
send without a continuation these are the same firing, so hosts that do not
use `after` see no change. A send with a continuation also fires for each
inline turn, under that turn's own id, which no `pending:queued` announced;
a host that keys queued rows by id ignores those by construction. Slow
per-cycle work in the callback, such as a sandbox snapshot, now runs after
every inline turn as well; move it to the end of the continuation.

### `cancel()` in the settle window

`cancel()` still returns `false` while a send without a continuation
settles. While a send with one settles, it returns `true`, aborts the
operation's signal, and the continuation never starts; the handle rejects
with `AxleAgentAbortError`.
