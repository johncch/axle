# Migrating to Axle 0.35.0

0.35.0 adds continuations: a send can carry `after`, a program that runs
once the turn has settled, holds the queue until it returns, and runs
further turns inline. `AgentResult` and `AgentErrorResult` gain `after`,
and `onSettled` now fires after every turn that commits, which is once per
send unless the send carries a continuation. Nothing is removed.

The Axle CLI is a separate product; its changes are recorded in
[packages/axle-cli/CHANGELOG.md](../packages/axle-cli/CHANGELOG.md).

---

## Breaking changes

### `AgentResult` and `AgentErrorResult` gain a required `after`

Code that constructs these objects itself, such as a test double for
`agent.send()`, stops compiling until it adds `after: []`. Code that reads
results is unaffected.

## Additions

### `after` on `send()`

```ts
const handle = agent.send("Summarize the report.", {
  after: async (result, ctx) => {
    for (let attempt = 0; attempt < 3; attempt++) {
      const verdict = await judge(result);
      if (verdict.ok) break;
      result = await ctx.send(verdict.feedback);
    }
  },
});
agent.send("Next question."); // waits until the continuation returns
```

The continuation runs after the send's turn settles with a result, `ok` or
not; a turn whose handle rejects (cancelled, a fatal tool error, a setup
failure) skips it. It holds the queue until it returns. `ctx.send()` runs
an inline turn: the same arguments as `send()` without `after`, an ordinary
turn in every way except that it starts at once with no `pending:queued`,
resolved with the turn's result after that turn's `onSettled` has
resolved. Inline sends run one at a time in call order and return a
promise, not a handle. `ctx` also carries `signal`, `id` (the send's user
turn id), and read-only `messages` and `pending`.

`cancel()` during a continuation aborts `ctx.signal` and any inline turn in
flight and rejects the handle; before it starts, it never starts. `stop()`
keeps its tool-batch meaning for an inline turn in flight. `clear()` never
touches a continuation. A continuation that throws rejects the handle and
the queue continues. A manual `compact()` carries no continuation, and an
inline turn carries none.

`Continuation`, `ContinuationContext`, `InlineSendOptions` and `InlineTurn`
are exported.

### `after` on results

The handle resolves when the continuation returns, with the inline turns
listed in order under `result.after`, each an `InlineTurn`: the `userTurn`
it sent and its own `ok`, `response`, `turn` and `usage`. The top-level
fields stay the message you sent and its reply; a caller wanting the
corrected answer reads the last entry. Inline responses are typed
`unknown`, since only the continuation saw the inline send's schema. A send
without a continuation resolves with `after: []`.

## Behavior changes

### `onSettled` fires per committed turn

It used to fire once per operation. It now fires after every turn that
commits and once for an operation that ran without opening a turn. For a
send without a continuation these are the same firing, so hosts that do not
use `after` see no change. A send with a continuation also fires for each
inline turn, under that turn's own id, which no `pending:queued` announced;
a host that keys queued rows by id ignores those by construction. Slow
per-cycle work in the callback, such as a sandbox snapshot, now runs after
every inline turn as well; move it to the end of the continuation.

### `cancel()` in the settle window

`cancel()` still returns `false` while a send without a continuation
settles. While a send with one settles, it returns `true`, aborts the
operation's signal, and the continuation never starts; the handle rejects
with `AxleAgentAbortError`.
