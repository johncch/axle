# Surfacing Model Refusals

Working note for AXL-67, "Surface model refusals instead of dropping them"
(0.33.0). The normative record is the Refusals section of
`docs/architecture/provider-content.md`; this note is how we got there.

## Starting point

Each provider reports a refusal differently, and Axle lost most of it. A
local script fed each provider's documented events through the adapters and
`stream()`, with no API calls:

| Provider         | Signal                                   | Result before                                              |
| ---------------- | ---------------------------------------- | ---------------------------------------------------------- |
| OpenAI           | `refusal` content part                   | `ok: true`, `finishReason: "stop"`, empty content          |
| OpenAI           | `response.incomplete` (`content_filter`) | `ok: false`, "Stream ended without a completion signal"    |
| Anthropic        | `stop_reason: "refusal"`, no output      | `ok: true`, `finishReason: "error"`, empty content         |
| Anthropic        | `stop_reason: "refusal"` after some text | `ok: true`, `finishReason: "error"`, the partial text kept |
| Chat Completions | `delta.refusal`                          | `ok: true`, `finishReason: "stop"`, empty content          |
| Chat Completions | `finish_reason: "content_filter"`        | `ok: true`, `finishReason: "error"`                        |
| Gemini           | `promptFeedback.blockReason`             | `ok: false`, `kind: "model"`, type `Blocked`               |
| Gemini           | `finishReason: SAFETY`                   | `ok: false`, `kind: "model"`, type `FinishReasonError`     |

The ticket asked whether a Gemini blocked response behaves like a blocked
prompt. It did: both were model errors, indistinguishable from a rate limit
except by the error type string.

## Decision: a failure kind, with nothing stored

A refusal is `ok: false` with `error: { kind: "refusal", refusal, message }`,
and `refusal` is `{ text?, category? }`. The refused step is not stored.

Reasons:

- `if (!result.ok)` is the check every caller already makes. A refusal that
  is `ok: true` with a special finish reason is still an answer to any caller
  that does not look further, which is the defect being fixed.
- An `Instruct` call needs no rule of its own. `stream()` only parses an
  `ok: true` result, so a refused `Instruct` returns the refusal.
- Nothing stored means nothing to convert on the next request. The follow-up
  is the same conversation a model error leaves behind.
- The turn layer needed no change: a stream `error` event already becomes
  `error: { type: kind, message }` on the turn.

Rejected:

- `ok: true` with a `refusal` finish reason and a refusal part on the
  message, for the first reason above.
- `ok: false` and also storing the refused message with a `refusal` part.
  Anthropic and Gemini return nothing to send back, Anthropic's guide says to
  discard partial output, and the part would need a send-back rule on four
  providers for content none of them requires.

Costs, accepted:

- The conversation history does not record that a refusal happened. The
  turn does, and so does the result.
- After an Anthropic refusal the refused user message is still in an
  `Agent`'s history. Anthropic says continuing without removing it tends to
  be refused again. Axle does the same thing it does after a model error and
  leaves the choice to the caller.
- Gemini block failures used to carry the raw chunk, so `safetyRatings` were
  reachable. A refusal has no `raw`. Anthropic's `recommended_model` and
  fallback credit token are not kept either. If one of these is needed, the
  place for it is a provider-tagged field on `Refusal`, as `continuity` is on
  a thinking part.

## How it travels

Adapters emit a new terminal chunk, `refusal`, in place of `complete`. The
step reader returns a `refused` outcome, and the loop in `stream()` turns it
into the failure and counts its usage. Refusal text is not streamed: OpenAI's
`response.refusal.delta` and Chat Completions' `delta.refusal` are
accumulated and delivered once, on the failure.

Which Gemini finish reasons count is a judgement: `SAFETY`, `RECITATION`,
`BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, and the three image variants are
refusals; `LANGUAGE`, `OTHER`, `MALFORMED_FUNCTION_CALL`, and the tool-call
reasons stay model errors. Every `promptFeedback.blockReason` is a refusal.

## OpenAI truncation, fixed alongside

Handling `content_filter` meant handling `response.incomplete`, which the
adapter had no case for. The same event carries `max_output_tokens`, so a
response cut off at the output cap failed with "Stream ended without a
completion signal" and lost its text. Observed on 2026-10-02 (`gpt-6-luna`,
`max_output_tokens: 16`): the stream ends with `response.incomplete` and
`incomplete_details: { reason: "max_output_tokens" }`, and no
`response.completed` follows. It now finishes with `finishReason: "length"`,
confirmed with the same request through `generate()`.
Any other reason becomes a model error naming it. The adapter's old check for
`incomplete_details` on `response.completed` never matched and is removed.

## Verification

`packages/axle/tests/providers/refusals.test.ts` runs each signal through the
provider's real request function with a scripted client, then through
`generate()`, `stream()`, an `Instruct` call, and `Agent`. It also checks
that the request after a refusal holds only the two user messages. The file
was written first and failed on 31 assertions.

No refusal was observed live:

- Anthropic's documented test string was answered as ordinary text on
  `claude-haiku-4-5` and `claude-sonnet-5-5`.
- A structured-output request that asked `gpt-6-luna` to decline came back
  as JSON, with no `refusal` part.
- Provoking a real refusal means sending a request a provider's safeguards
  block. We did not do that; the fixtures follow the providers' documented
  shapes and SDK types.

## Not done

- No `checks/` scenario, for the reason above.
- Refusals written as ordinary text are not detected.
- Anthropic's server-side fallback (`fallbacks`, `recommended_model`,
  fallback credit) is not used.
