# Meter: a sink that prices the turn stream, and the catalog that owns its loading (AXL-93)

Working note. The ticket asked for a `Meter` that accumulates usage and
cost from turn events. Building it exposed that `ModelCatalog`'s API made a
correct Meter impossible to write without every consumer repeating the
catalog's job, so the catalog changed with it.

## Starting point

Invariant 6 of agent-state.md: usage accounting is the consumer's. Every
`turn:end` carries `usage` with one `UsageEntry` per provider request, and
the CLI's runners summed `in`/`out` by hand. Nothing priced anything. The
2026-10-08 catalog was `await ModelCatalog.open()` plus
`if (catalog.stale) void catalog.refresh()` at every site; a site that
forgot the second line ran with an empty catalog that answered `undefined`
to every `lookup`, the same answer as a model it does not list.

## What landed

`Meter` is a sink: `agent.on(meter.apply)`, the sibling of `Transcript`.
It folds `turn:end` into `usage` (restored rows plus applied) and
`observedUsage` (applied only). `cost` and `observedCost` price the rows
against the catalog on every read and store nothing. A `Cost` is
`{ usd, priced, unpriced, pricedWith? }`; each unpriced row says why
(`loading | unavailable | no-catalog | no-provider | unlisted | no-price`).
`priced()` awaits the catalog's `ready` and returns `cost`.

`ModelCatalog.open()` is synchronous and returns a catalog in `loading`.
It reads the cache; with none it fetches once, bounded by `fetchTimeout`;
with a stale one it serves the copy and refreshes behind it; when
`unavailable` it retries at `retryDelays`. Consumers see `state`, `ready`
and `onChange`. `stale` and `fetchedAt` as getters are gone; both live on
`state` when `loaded`.

`UsageEntry` gains `at`, when the provider finished the request. `Cost`
gains `pricedWith`, the `fetchedAt` of the catalog that priced it.
`Transcript.apply` became a bound property so both sinks attach the same
way.

The CLI keeps two meters on one catalog: the session's (persisted as
`meter` in the session file, restored on resume) and the run's (what the
bar, batch footer and summary show). It awaits `ready` once at startup, so
the first run on a machine waits for one download and every later run pays
a file read.

## The debate, in order

**Should the Meter work around the catalog or should the catalog be fixed?**
The first draft had the Meter check `catalog.size === 0` and report
`loading`. The owner's objection: that is working around poor API design,
and both should be solved properly. The fix moved loading into the catalog
and gave it an explicit state machine. Every later site is simpler for it.

**Sync or async `open()`?** The design was read back as synchronous, then
implemented as `async` because the cache read is async, and mentioned only
in passing. The owner caught it in the code. The point that settled it:
either the catalog promises to run in the background and gives the
consumer the tools to handle async (`state`, `ready`, `onChange`), or the
whole thing is sync and the consumer works around it. A network fetch in
the background with a file read that blocks is neither. Synchronous
`open()` with every load behind it is the consistent choice.

**Latency on pricing.** With a two-day-old cache and models.dev taking
fifteen seconds, a price read at six seconds is served from the stale copy
and reports `loaded`; the refresh finishes or times out on its own, and
neither blocks. Most clients therefore pay file-system latency once they
have any cache. The worry that `db.write(await meter.cost)` becomes a time
bomb if the read can hang is answered by the split: `cost` is a getter and
cannot hang; `priced()` is bounded by `ready` and never rejects.

**Timestamps.** First dismissed as unnecessary on rows. Reversed on the
vendor argument: someone billing a customer wants to know when the request
was handled, and a catalog that one day carries dated price sheets can
price an old row only if the row knows its date. So `at` goes on the row
(the record) and `pricedWith` on the cost (the provenance), both ISO
strings because they are persisted and `TimingInfo` already uses strings.

**Two meters or one.** Resuming a session and showing "this run" in the
bar while saving "all time" to the file wanted a filter on one meter or two
instances. Two instances is less code and no cursor.

## Decided not yet

- `maxStale`, the age past which a stale copy is treated as `unavailable`
  (HTTP stale-while-revalidate / stale-if-error semantics).
- Consumer price overrides on the catalog, surfaced as `match: "override"`.
- `meter.onChange`. Hosts redraw on `turn:end` and `catalog.onChange` today.
