# Analyze: functions for understanding what an agent did (AXL-101)

Working note. The ticket asked for a way to give hosts what the Agent
already knows about a conversation's errors, so that Sunnyday could stop
running an LLM judge to find them.

## Starting point

AXL-91 had built and dropped an `Incidents` sink on the event stream. The
ticket that replaced it proposed a **digest**: a versioned, content-free
record of a run, with a summary block of counts and the turns with their
content stripped. It came with 18 questions over an 18-turn example
conversation that the record should answer.

## How the design moved

The digest did not survive the first usage sketch. Writing out how each of
the 18 questions would be answered showed that most were a read of the
turns themselves, and the record added little beyond the summary. The
summary was a fixed set of counts where each host wants its own.

Reading Sunnyday settled what a consumer needs. Its errors judge stores
`{ tool, message, recovered }` per error, with "recovered" defined as the
agent moving past the error. Its `compactedTruncatedTurns` reduces turns
for three other judges and one assistant tool. So there were two jobs:
facts that need no content, and content prepared for a reader.

The shape went through four forms:

1. A `Digest` object.
2. Two functions, `toolErrors(turns)` and `trajectory(turns)`. Correct for
   Sunnyday and too small a slice of "understand what the agent did".
3. One uniform row type from `flatten(turns)`, borrowed from distributed
   tracing. Every question that spanned a part and its turn needed a
   lookup by id.
4. A vocabulary of named filters. The first sketch was a chained
   collection (`analyze(turns).tools.errors.count`). Comparing libraries
   moved it to plain arrays with exported predicates, the way d3-array,
   date-fns and the `unist-util-*` packages work.

Three later decisions simplified it further. Subagents are sequestered and
merged on request, because merging is one call and separating is a filter
on every question. A turn keeps its parts in order, with the kind lists as
views of the same objects. And `errors` holds the segments that failed, so
there is no error type.

## Names

- `trajectory` became `simplify`. The word had to mean removing what is
  not content and say nothing about selecting or interpreting, which ruled
  out `summarize`, `distill`, `extract`, `curate` and `outline`.
- The shared base of every item is `Segment`. `Located`, `Item` and
  `Observation` were considered.
- `flatten` over `merge` and `rollup`, since nothing is combined.

## What `Turn` gained first

`analyze` reads only turns, so four changes came before it:

- `cancelReason` on a turn the timeout cancelled.
- `error` on a turn that ended on a thrown error.
- The user turn opens before MCP tools are listed, so a listing failure is
  an error turn that keeps the user message.
- A failed subagent's tool error no longer embeds the child's failure as
  JSON.

Two things were deliberately left alone: a queued send cancelled before it
started stays dropped, and a throwing `onStart` stays a refused start.
Compactor token usage stays unreported, and no error codes were added.

## Consequences found while building

- Opening the user turn first means a cancel during the MCP listing now
  ends the agent turn `cancelled` and keeps the user message, where it
  used to drop the send. This matches a cancel during `beforeTurn`
  compaction.
- After a failed listing, a retry is a second send, so the conversation
  holds two user messages in a row.
- A user turn has no part segments. `texts` is what the agent wrote.
- Turns stored before 0.37 can have `status: "error"` with nothing saying
  why. `analyze` reports those with error type `unknown`.

## Testing it against the checks

After the five phases were built, the question was whether `analyze` could
serve the repo's own live provider checks. If it could not, that would say
something about the design.

An audit of the 82 check cases found 22 that drive an Agent. `analyze`
answers the question about what the agent did for 17 of them. The other
five have specific reasons:

- `agent-step-hook` asserts on steps, which turns do not record.
- The four partial-cancel checks test `agent.messages`, the history sent
  to the model, after a cancel. That is a protocol test.

Within the 17, four kinds of assertion stay outside `analyze`: the
reply's content, the order of message roles, what a callback saw, and
usage rows by provider.

The audit found two fields the checks read that segments lacked, and both
were added: `threadId` on a turn segment and `callId` on a deferred tool
call.

The other 60 cases call `generate()` or `stream()`. That looked like a
coverage imbalance until one fact was checked: `generate()` is
`stream(...).final`, and the Agent calls `stream()`. All three run the same
request and tool-loop code, so a `generate()` check of what a provider
accepts is already as close to the thing as it can be. The real gap was
narrower: no live check verified that real provider output lands in
turns. Every Agent check with a transcript covered text, local tools,
subagents, compaction or deferred tools only.

Five checks were added. Three of them compare what the model-facing
history holds with what the transcript records, for web search and
citations, thinking, and code execution. The other two cover a tool that
fails once and is retried, and a turn that times out.

## What the new checks found

`agent-web-search` failed on Gemini on its first run: history held a
citation and the turn had none. Gemini sends grounding citations after the
text they support has closed. The step reader attached the citation to the
right text part in the message by index, but the `text:citation` stream
event did not carry that index, and the turn builder applied it only to a
text part that was still open. `thinking:update` had the same defect.

The fix gives every `text:*` and `thinking:*` stream event a required
`index`, and the turn builder resolves parts by it. A smaller fix was
considered, attaching a late citation to the most recent text part, and
rejected: it is right for Gemini's case and wrong in general, and the
index already existed one layer down.

## Considered and dropped

- **Steps on turns.** A step index on each part, and a count on the turn,
  were designed and then dropped. No check needed them: the one check that
  asserts on steps is testing the `onStep` hook, and the request count is
  already `usage.breakdown.length`. It is easy to add later and hard to
  take away if done badly.
- **`analyze` over messages.** Messages are closer to the wire and are
  what `generate()` returns, but they are working state: compaction
  replaces them, a cancel repairs them, and a failure leaves no message.
  Turns are the record of a long run, which is what `analyze` is for.
- **Carrying content on segments.** Raised again when the checks turned
  out to assert on content half the time. `partOf` already covers it.

## Not done here

Sunnyday still has to adopt it: replace the `trajectory.errors` judge with
`a.tools.filter(failed)`, and `compactedTruncatedTurns` with `simplify`.

The CLI `exec` tool returns failures as successful strings, so `analyze`
cannot see them. That is a separate question.
