# Migrating to Axle 0.37.0

0.37.0 changes the `reasoning` setting and adds a per-step hook.

- **The setting names a model's own knobs:** `reasoning` is `"default"` or
  `{ enabled?, effort?, display? }`. `enabled` is the model's on/off switch
  and `effort` its depth. `"off"` and `"on"` are gone.
- **Six efforts, sent as written:** `minimal`, `low`, `medium`, `high`,
  `xhigh` and `max`. Axle maps no effort to another.
- **The catalog says what a model takes:** `ModelCatalog` records each
  provider's reasoning controls, and `reasoningControl()` reads them as the
  efforts to offer and the setting to send for an on/off control.
- **`agent.onStep`:** an awaited hook at the end of each step, so a host can
  save usage and state while a turn runs.
- **An `Instruct` schema is a JSON Schema:** pass one directly, or a Zod
  schema as before. The prompt carries the JSON Schema in place of an
  example, any schema Zod can convert is accepted, and `parseResponse()`
  and `Instruct.parse()` are async.
- **A remote send carries the `Instruct` as data:** the served side renders
  it, and a host's `send` case becomes `Instruct.fromJSON(command.instruct)`.

The Axle CLI is a separate product; its changes are recorded in
[packages/axle-cli/CHANGELOG.md](../packages/axle-cli/CHANGELOG.md).

## Breaking changes

These need a change at existing call sites, or to an exhaustive switch.
Each one is a type error until changed.

### `"off"` and `"on"` are replaced by `enabled`

`ReasoningSetting` was
`"default" | "off" | "on" | { effort, display? }` and is now:

```ts
type ReasoningSetting =
  "default" | { enabled?: boolean; effort?: ReasoningEffort; display?: "visible" | "hidden" };
```

| 0.36                            | 0.37                                                |
| ------------------------------- | --------------------------------------------------- |
| `reasoning: "default"`          | unchanged                                           |
| `reasoning: "off"`              | `reasoning: { enabled: false }`                     |
| `reasoning: "on"`               | `reasoning: { effort: "medium" }`, the same request |
| `reasoning: { effort: "high" }` | unchanged                                           |

`"on"` meant medium, and many models have no `medium`: it is missing from
28% of the effort lists models.dev records, including every model that
takes `low, high, max`. There is no setting that means "on" for every
model. If the model is chosen at run time, ask the catalog what to send:

```ts
const found = catalog.reasoningControl(model, { provider: "anthropic" });
new Agent({
  provider,
  model,
  reasoning: thinkingOn ? (found?.suggested ?? { effort: "medium" }) : { enabled: false },
});
```

At run time, a string other than `"default"`, a boolean, and an object
with an unknown key each reject with an `AxleError` (`INVALID_OPTIONS`).

### `ReasoningEffort` has six members

`ReasoningEffort` was `"low" | "medium" | "high"` and is now
`"minimal" | "low" | "medium" | "high" | "xhigh" | "max"`. An exhaustive
`switch` or a `Record<ReasoningEffort, …>` needs the three new members.

An effort reaches the provider unchanged, and the provider rejects one the
model lacks: Anthropic has no `minimal`, and `xhigh` and `max` exist only
on newer models. OpenRouter and Together AI can map an effort a model
lacks to one it has.

### Saved `CatalogData` is version 5

`CatalogData.version` is `5`: a provider entry can carry `reasoningOptions`.
`parseCatalogData` and `ModelCatalogStore.load` return nothing for a file
saved by 0.36, the same as for any older copy, so the next
`refreshIfStale()` fetches. No code changes unless you build `CatalogData`
by hand, where `version: 4` becomes `version: 5`.

---

### `parseResponse()` and `Instruct.parse()` return a promise

A schema's validator may answer asynchronously, so both now do.

| 0.36                                   | 0.37                                         |
| -------------------------------------- | -------------------------------------------- |
| `const value = parseResponse(text, s)` | `const value = await parseResponse(text, s)` |
| `const value = instruct.parse(final)`  | `const value = await instruct.parse(final)`  |

`agent.send()`, `stream()` and `generate()` already return promises and are
unchanged.

### `OutputSchema` is a JSON Schema or a Standard Schema object

`OutputSchema` was `z.ZodTypeAny` and is now:

```ts
type OutputSchema = StandardOutputSchema | JsonSchema;
```

A Zod schema is a `StandardOutputSchema`, so `new Instruct({ schema: z.object({...}) })`
is unchanged and `response` keeps its type. Code that names the type and
calls Zod methods on it (`schema.parse()`, `schema.shape`) needs its own Zod
type. Zod must be 4.2 or later, which Axle already required.

### Instruct inputs are strings, numbers, booleans or `null`

`InstructInputs` was `Record<string, unknown>` and is now
`Record<string, InstructInput>`, with
`InstructInput = string | number | boolean | null`. Inputs cross the wire
with a remote send, and these are the values that render the same on both
sides. An object or array already rendered as `[object Object]`.

| 0.36                            | 0.37                                          |
| ------------------------------- | --------------------------------------------- |
| `withInput("when", new Date())` | `withInput("when", new Date().toISOString())` |
| `withInput("tags", ["a", "b"])` | `withInput("tags", ["a", "b"].join(", "))`    |
| `withInput("count", undefined)` | `withInput("count", null)`                    |

### A remote `send` command carries the `Instruct`

The command was `{ type: "send", id, prompt, files?, metadata? }`, with the
prompt rendered by the client. It is now `{ type: "send", id, instruct }`,
where `instruct` is `InstructData`. A host's `send` case changes:

```ts
// 0.36
const instruct = new Instruct({ prompt: command.prompt, vars: "optional" });
for (const file of command.files ?? []) instruct.addFile(file);
agent.send(instruct, { id: command.id, metadata: command.metadata });

// 0.37
agent.send(Instruct.fromJSON(command.instruct), { id: command.id });
```

A 0.36 client and a 0.37 host do not interoperate: `parseAgentCommand`
returns `null` for the old shape. Deploy both sides together.

## Behavior changes

### `agent.messages` grows during a turn

The Agent now adds a turn's messages as each step ends. It used to add them
all when the turn ended. A step is one model call and the tools it asked
for, so an assistant message that asks for tools appears together with its
tool results.

What a turn leaves behind is unchanged, including a failed or cancelled
turn, which keeps its user message and the steps it finished. What changes
is when a reader sees it: code that reads `agent.messages` while a turn runs
(from a tool, an event listener or a hook) now sees the finished steps.

### `turn:end` usage counts failed requests, and orders a batch's rows by call

A turn's `turn:end` usage is now the sum of what its steps report to
`onStep` (see Additions), and equals the `usage` on the send's result. Two
things differ from before:

- A request that failed or was refused after the provider reported usage is
  included. It was on `result.usage` already and missing from `turn:end`.
- When several subagents run in one tool batch, each subagent's rows stay
  together and the groups follow the order the calls were requested. They
  used to follow the order the calls finished. Each row still carries `at`.

A consumer that totals `turn:end` usage sees slightly higher totals on
turns with a failed request; they now match what the provider billed.

### Custom `StreamHandle` implementations add `onStep`

`StreamHandle` has a new required method, `onStep(callback)`. A wrapper or
mock that implements the interface adds it.

---

### The schema is stored on the message, not written into its text

The output instructions used to be part of the user message: a field list
and an example object with placeholder values, ahead of the prompt.

- **The stored message is the prompt.** `agent.messages` and the user turn
  no longer contain output instructions. The message carries the JSON Schema
  as `output: { schema }`.
- **`instruct.render()` returns the prompt alone.** It no longer includes
  the instructions. Code that sent `render()` to a model itself and relied
  on them now passes the `Instruct` to `stream()` or `generate()`.
- **The request shows the schema, not an example.** For a provider without
  native output, each request's copy of the message gets this ahead of it:

  ```
  # Output Format Instructions

  Return only valid JSON matching this JSON Schema. Do not wrap it in markdown. Do not include prose before or after the JSON.

  {
    "type": "object",
    ...
  }
  ```

  Value constraints such as `.min()` and `.regex()` now reach the model. A
  schema with long patterns, such as `z.iso.datetime()`, makes a longer
  request.

- **Saved conversations from 0.36** keep the old instructions in their
  message text and have no `output`, so they are sent as they were.

### Schemas that used to throw are accepted

`Unsupported Zod schema: <class>` is gone. `.nullable()`, unions, tuples,
records, `z.email()` and the other formats, and a root that is not an
object are all accepted. A schema Zod cannot convert to JSON Schema, such
as one with `z.date()`, throws Zod's error.

### The model is shown the schema's input side

With `.transform()` the model is shown the type the transform takes, and a
key with `.default()` is not required. The parsed `response` is the
schema's output, as before.

## Additions

### `agent.onStep`: an awaited hook at the end of each step

A host can now save usage and state while a turn runs, instead of once at
`turn:end` and `onSettled`.

```ts
agent.onStep(async (step) => {
  await db.insert(usageLedger).values(
    step.usage.breakdown.map((row, i) => ({
      turnId: step.turnId,
      step: step.index,
      row: i,
      ...row,
    })),
  );
  await saveSession({ sessionId: agent.sessionId, messages: agent.messages });
});
```

One turn that calls a tool and then answers fires twice:

| Step                       | `index` | `usage.breakdown` | `agent.messages` ends with |
| -------------------------- | ------- | ----------------- | -------------------------- |
| Model call and its tools   | 0       | 1 row             | assistant, tool results    |
| Model call with the answer | 1       | 1 row             | assistant                  |

`turn:end` then carries both rows, in that order. It is the authoritative
record of what the turn cost; a step's usage is the early copy, so a turn
that never reaches `turn:end` does not lose its spend. A host that saves per
step replaces the turn's rows with the `turn:end` usage when it arrives.

- `index` counts the turn's steps from 0, compactions included, so it can
  run ahead of the model calls `maxSteps` counts.

- It fires however the step ended: answered, failed, refused or cancelled.
- A subagent's rows arrive on the step whose tools ran it.
- A compaction whose callback ran is a step with empty usage, including a
  direct `agent.compact()`.
- `agent.messages` is always a conversation the provider accepts when the
  hook fires, so what you save can be restored and sent to.

The agent waits for the callback before it sends the next request. A
callback that throws stops the turn there: the send rejects with the thrown
error, as for `onStart`. Catch your own errors if saving should be best
effort. `cancel()` during a callback takes effect when it returns.

`stream()` has the same hook as `handle.onStep(callback)`. It receives
`{ usage, messages }` for the step.

### `enabled: true` turns thinking on without naming an effort

For a model or provider that has an on/off switch:

| Route                                          | `{ enabled: true }` sends                    |
| ---------------------------------------------- | -------------------------------------------- |
| Anthropic                                      | `thinking: { type: "adaptive" }`             |
| Together AI, OpenRouter                        | `reasoning: { enabled: true }`               |
| Gemma 4 on Gemini                              | `thinkingLevel: "high"`                      |
| OpenAI, generic endpoints, other Gemini models | nothing: Axle rejects with `INVALID_OPTIONS` |
| Models that only take a token budget           | nothing: Axle rejects with `INVALID_OPTIONS` |

`{ enabled: true, effort }` is the same as `{ effort }`. An object that
sets neither `enabled` nor `effort`, or sets `enabled: false` beside an
effort, is rejected.

For Gemma 4 on Gemini, `{ enabled: false }` sends `thinkingLevel: "minimal"`,
which is how Google spells off for those models.

### `xhigh` and `max` no longer need `providerOptions`

```ts
// before
generate({
  provider,
  model,
  messages,
  reasoning: { effort: "high" },
  providerOptions: { output_config: { effort: "xhigh" } },
});

// after
generate({ provider, model, messages, reasoning: { effort: "xhigh" } });
```

### `REASONING_EFFORTS`

The six efforts as a readonly list, lowest first, for a host that renders a
picker or validates input:

```ts
import { REASONING_EFFORTS } from "@fifthrevision/axle";
// ["minimal", "low", "medium", "high", "xhigh", "max"]
```

`ReasoningConfig` is the object form of the setting.

### Every effort has a budget on budget-only models

Claude Haiku, Opus and Sonnet 4.5 and Gemini 2.5 take a token budget
instead of a named effort. The presets now cover all six:

| Effort  | Budget |
| ------- | ------ |
| minimal | 1,024  |
| low     | 2,048  |
| medium  | 8,192  |
| high    | 16,384 |
| xhigh   | 20,480 |
| max     | 24,576 |

Low, medium and high are unchanged.

### `ModelCatalog.reasoningControl()` and `reasoningOptions`

A `lookup()` that matches a provider's own id returns `reasoningOptions`
where models.dev records them: `{ type: "effort", values }` in the
provider's words, `{ type: "budget", min?, max? }`, or `{ type: "toggle" }`.

`reasoningControl(model, { provider })` reads that record as the kind of
control to show and the setting to send:

```ts
catalog.reasoningControl("claude-sonnet-5", { provider: "anthropic" });
// → { control: "levels", efforts: ["low", "medium", "high", "xhigh", "max"], suggested: { effort: "medium" }, id: "anthropic/claude-sonnet-5" }
```

| `control`  | `efforts`                                                         | `suggested`                                                  |
| ---------- | ----------------------------------------------------------------- | ------------------------------------------------------------ |
| `"levels"` | The provider's listed efforts, or all six for a budget-only model | `{ effort }`, the one closest to medium, the higher on a tie |
| `"toggle"` | `[]`                                                              | `{ enabled: true }`                                          |
| `"none"`   | `[]`: the model does not reason, or always does                   | absent                                                       |

`suggested` is a `reasoning` setting: pass it as `reasoning: found.suggested`
or spread it to add `display`. The method returns `undefined` when the
catalog has no record for that provider's model. The answer is advisory:
Axle never checks a request against it, and it does not say whether a
model can be turned off.

### A JSON Schema object as an `Instruct` schema

`schema` takes a plain JSON Schema object. Axle sends it as written and
returns the parsed JSON as `unknown`, without validating it. `JsonSchema`
and `StandardOutputSchema` are exported types.

### `output` on messages, turns and `turn:end`

- `AxleUserMessage.output?: { schema: JsonSchema }`: the schema a message
  asks its answer to match. A hand-built message with `output` passed to
  `stream()` has its schema applied.
- `Turn.output?: TurnOutput` and `turn:end`'s `output`:
  `{ schema, mode? }`, with `mode` `"native"` or `"prompt"` on an agent
  turn. `TurnOutput` and `OutputMode` are exported types.

### `AIProvider.structuredOutput`

A provider sets `structuredOutput: true` to receive the schema as
`ProviderStreamParams.output` in place of prompt text. No built-in provider
sets it yet. A custom provider that leaves it unset needs no change.

### `Instruct.toJSON()` and `Instruct.fromJSON()`

`toJSON()` returns `InstructData`: the prompt template, inputs, variable
mode, references, context sections, files, metadata, and the schema as JSON
Schema. `Instruct.fromJSON(data)` rebuilds it. A rebuilt `Instruct` holds a
JSON Schema, so its answer is parsed as JSON and typed `unknown`.
