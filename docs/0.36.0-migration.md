# Migrating to Axle 0.36.0

0.36.0 adds deferred tools: a tool definition with no `execute`, answered by
whoever holds the loop through `onToolCall`. To carry that, `onToolCall` on
`stream()` and `generate()` changes shape and stops intercepting executable
tools.

The Axle CLI is a separate product; its changes are recorded in
[packages/axle-cli/CHANGELOG.md](../packages/axle-cli/CHANGELOG.md).

---

## Breaking changes

### `onToolCall` answers deferred tools only, and takes a call

Before, `onToolCall(name, parameters, ctx)` ran before every tool's
`execute`; a non-null `ToolCallResult` replaced the tool's own result and
`null` fell through. It now receives one `DeferredCall`, `{ id, name, input }`,
and the `ToolContext` an `execute` receives, and returns what an `execute`
returns: a string or `ToolResultPart[]`. It is consulted for the deferred
tools in `tools` and never for an executable one.

```ts
// before
stream({
  tools: [search],
  onToolCall: async (name, params) =>
    name === "search" ? { type: "success", content: await lookup(params) } : null,
});

// after: an executable tool runs through its own execute
stream({ tools: [search] });

// after: a tool the caller answers is a deferred tool
const askUser = {
  type: "deferred",
  name: "ask-user",
  description: "Ask the person a question",
  schema: z.object({ question: z.string() }),
} satisfies DeferredTool;
stream({
  tools: [search, askUser],
  onToolCall: (call) => (call.name === "ask-user" ? prompt(call.input.question) : undefined),
});
```

A callback that answered calls to names with no registered tool now has no
effect on them: such a call is `not-found`, as it was without a callback.
Register a `DeferredTool` under that name to keep answering it. To return an
error result, throw; the message is the reason. A branch that returns nothing
has not answered: the call stays waiting (see below).

### A silent handler waits; `toolCall(id)` answers from outside

A deferred call settles by whichever comes first: the handler's return or
throw, `toolCall(id).answer()` or `.fail()`, the tool's `timeout`, or
cancellation. A handler that returns nothing, or no handler at all, leaves
the call waiting for the others; there is no `unanswered` error result.
`stream()`'s handle and `Agent` both have `toolCall(id)`, which returns
`{ answer, fail }` while that call is waiting and `undefined` once it has
settled.

```ts
const run = stream({ provider, model, messages, tools: [askUser] });
run.on((event) => {
  if (event.type === "tool:waiting") showPrompt(event.id, event.input);
});
run.toolCall(callId)?.answer("teal"); // when the person clicks
```

`generate()` returns no handle, so nothing outside its handler can answer.
It keeps failing fast: a call the handler does not answer, or any call when
there is no handler, is an error result at once. The only change there is
the result's shape, an `execution` error with the message
`No onToolCall answer for <name>` where it was an `unanswered` error.

### `action:waiting` carries `callId` and `name`

The event gains the tool call id and the tool name beside `input`, so a
consumer can build the handler's `DeferredCall` from the event without
looking the part up. A `Transcript` folds it unchanged.

### `send()` takes an `id` for its user turn

`SendMessageOptions.id` names the send's user turn: the id `pending:queued`,
`turn:user`, the user message and `onSettled` carry. Generated when omitted,
as before.

### `ctx.send()` no longer accepts `signal`

`InlineSendOptions` omits `signal`. In 0.35.0 the type accepted it and the
Agent ignored it: the inline turn always ran under `ctx.signal`. Passing
one is now a type error. Remove it, and cancel the operation (the handle's
`cancel()` or `agent.cancel()`) to abort an inline turn.

```ts
// before: compiled, and the signal never fired
await ctx.send("Review the draft", { signal: controller.signal });

// after
await ctx.send("Review the draft");
```

### `onSettled` fires once per operation, after the continuation

`onSettled` used to fire after every turn, before the send's continuation,
and again for each inline turn under that turn's own id. It now fires once
per send or manual compaction, after the continuation returns and before
the handle settles, with what the handle settles with: the result, its
`after` list included, or the rejection. Inline turns no longer fire it. A
callback that filtered out inline ids drops the filter; one that saved
after each inline turn saves inside the continuation instead:

```ts
// before: fired for the send's turn, then for "fix"
agent.onSettled((session) => save(session));

// after: fires once, after the continuation; save inside it per turn if needed
agent.send(text, {
  after: async (result, ctx) => {
    await ctx.send("fix");
    await saveMessages(ctx.messages);
  },
});
```

A throwing `onSettled` still cannot change the result. `cancel()` and
`stop()` return `false` while it runs, a continuation or not.

### `agent.on` delivers lifecycle events; `TurnEventCallback` is `AgentEventCallback`

`agent.on` now delivers the operation's lifecycle beside the turn events:
`operation:start { id, kind }`, `after:start { id }` and `after:end { id }`
around a continuation, `operation:end { id, outcome }`, and `agent:idle`.
Its callback type is `AgentEventCallback`, taking an `AgentEvent`; every
`AgentEvent` is a `TurnEvent`. `TurnEventCallback` is gone.
`Transcript.apply` reports the new events handled and folds nothing from
them, so `agent.on(transcript.apply)` is unchanged. A handler that switches
exhaustively on `event.type` gains five cases.

```ts
// before
const onEvent: TurnEventCallback = (event) => forward(event);

// after
const onEvent: AgentEventCallback = (event) => forward(event);
```

A send dropped before its turn opened, by a setup failure or a throwing
`onStart`, now emits `operation:end` after its `pending:dropped`. A send
withdrawn from the queue emits `pending:dropped` alone, as before.

`agent.status` is new: `{ phase: "idle" }` or `{ phase: "busy", id }` with
the running operation's id, busy through `onStart`, the continuation and
`onSettled`. It changes at `operation:start` and `agent:idle` and already
reads the new value when they are delivered. `agent:idle` arrives just
before `onIdle` fires, and `onIdle` is unchanged.

### `onStart` and `threadId` are new

`agent.onStart(({ kind, id, signal }) => …)` fires once an operation holds
the queue, before its turn opens, and is awaited; one that throws skips
the turn and the continuation, drops the pending turn, and rejects the
handle. A user turn sent inline through `ctx.send()` carries `threadId`,
the send's id, on its message and its `Turn`. New types: `StartCallback`,
`StartedOperation`, `OperationOutcome`. Additive.

### `Turn` carries an optional `cursor`

`Transcript.apply` accepts a turn event with a `cursor` string beside its
fields and records it on the turn that `turn:user` or `turn:end` closes.
Events from `agent.on` carry none, so turns folded locally are unchanged.
Additive.

### Remote agents (experimental, additive)

New exports: `InMemoryEventStore`, `toEventStreamResponse`,
`loopbackTransport`, `httpTransport`, `RemoteAgent`, `parseAgentCommand`,
`agentCommandSchema`, `commandOutcomeSchema`, and the types
`AgentCommand`, `CommandOutcome`, `AgentTransport`, `AgentSubscription`,
`AgentWelcome`, `StreamItem`, `StoredEvent`, `RemoteHandle`, `RemoteConnection`,
`RemoteSendOptions`,
`RemoteWaitingToolCall`, `HttpTransportOptions`, `HttpTransportError`.
The consumer-side ones are on `@fifthrevision/axle/ui` as well; the
schemas and `parseAgentCommand` are on the main entry only. Nothing
existing changes; see the README's _Remote agents_ section and
`docs/architecture/remote-agent.md`.

### `tools` accepts `AnyTool[]`

`StreamParams.tools`, `ToolRegistry.add()` and the registry's constructor take
`AnyTool`, which is `ExecutableTool | DeferredTool`. Code that passes
`ExecutableTool[]` is unaffected. `ToolRegistry.get()` still returns executable
tools only; `getDeferred()` and `deferred()` return the other kind.

### `Agent` offers deferred tools and answers them through `agent.onToolCall`

`AgentConfig.tools` takes `AnyTool[]`. A `DeferredTool` in it is offered to
the model like any other tool and its calls go to the handler registered with
`agent.onToolCall(handler)`, one per Agent. An Agent with a deferred tool and
no handler still runs: each call waits for `agent.toolCall(id)`, the tool's
`timeout` or `cancel()`. Nothing changes for an Agent whose tools all have
`execute`.

### New stream events

`tool:request` may carry `kind: "deferred"`, and `tool:waiting` fires when a
validated deferred call is handed to `onToolCall`. A consumer that switches on
`StreamEvent.type` exhaustively gains one case.

### New turn event and action part

`ActionPart` gains `DeferredAction`, `kind: "deferred"`, with statuses
`pending`, `waiting`, `complete`, `cancelled` and `error`, and `TurnEvent`
gains `action:waiting`. A renderer that switches exhaustively on `part.kind`
or on `TurnEvent["type"]` gains one case each. A `Transcript` folds both
without change. `isActionOf(tool, part)` narrows a part to one deferred
tool's action with its input typed; `isCall(tool, call)` does the same for
the handler.
