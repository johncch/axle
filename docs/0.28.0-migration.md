# Migrating to Axle 0.28.0

0.28.0 adds graceful turn interruption (`agent.stop()`), queue clearing
(`agent.clear()`), and expands the experimental compaction API with automatic
turn triggers and a built-in prompt-based implementation.

Two source changes may be required:

- Applications using experimental compaction replace
  `agent.onCompaction(compact)` with `agent.setCompaction({ compact })`, and
  cancelled `agent.compact({ signal })` calls now reject instead of resolving
  `null`.
- Custom `StreamHandle` wrappers or mocks add `onToolBatchComplete(callback)`.

Applications that do neither can upgrade without changing existing `send()`
calls. `stop()` is opt-in.

---

## TL;DR

```ts
import { Agent, PromptCompactor } from "@fifthrevision/axle";

const agent = new Agent({ provider, model });

const compactor = new PromptCompactor({
  provider,
  model,
  prompt:
    "Create a continuation summary. Preserve decisions, constraints, completed work, and open tasks.",
  thresholdTokens: 100_000,
  targetTokens: 20_000,
});

agent.setCompaction({
  compact: compactor.compact,
  triggers: {
    beforeTurn: true,
  },
});

const initial = agent.send("Build the feature.");

// later, from an event handler while the turn is executing:
agent.stop(); // returns false if no turn is executing yet
const correction = agent.send("Make the button blue.");

const initialResult = await initial.final;
const correctionResult = await correction.final;
```

`initialResult` belongs only to the initial handle, which settles at the stop
boundary. `correctionResult` belongs only to the follow-up handle.

## Interrupting the active turn

### `agent.stop()` finishes the turn at a tool-batch boundary

`send()` remains the only way to schedule a turn, and queued sends stay FIFO.
`stop()` asks the currently executing turn to wrap up gracefully instead of
running its tool loop to completion:

```ts
const h1 = agent.send("Build the feature.");

// later, from an event handler while h1 is executing:
agent.stop(); // returns false if no turn is executing yet
const h2 = agent.send("Make the button blue.");
```

`stop()` does not abort the active provider request or interrupt running
tools. When the active model turn requests tools, Axle:

1. Executes the complete tool-call batch, including parallel tool calls.
2. Commits the assistant tool-call message and all tool results.
3. Settles the active handle without starting another provider request.

The transcript remains linear, and the committed batch is visible to the next
turn:

```text
user: h1
assistant: tool calls
tool: complete batch results
user: h2
assistant: h2 response
```

`h1.final` settles at the stop boundary; `h2` owns the next user and
assistant turns. Because a stopped turn ends on its tool-call exchange, a
plain send resolves with whatever text that turn produced (often empty), and
an `Instruct` send may resolve `ok: false` with a parse error — no final
answer exists yet by design.

`stop()` returns `false` when no turn is executing — including when called
synchronously after `send()`, before the turn has started on the microtask
queue. If the active model response requests no tools, the turn completes
normally. `stop()` never affects queued sends: they run afterwards in FIFO
order, and jumping the queue is not supported.

### `agent.clear()` drops queued work

`clear()` cancels every queued operation without touching the active turn.
Each cleared handle rejects with an `AxleAgentAbortError`, exactly as if it
had been cancelled individually, and commits nothing to history. It returns
the number of operations cleared.

Together, `stop()` and `clear()` recover full takeover semantics:

```ts
agent.stop(); // active turn settles at its tool-batch boundary
agent.clear(); // queued sends are dropped
agent.send("Make the button blue."); // runs as the very next turn
```

### Cancellation is handle-local

Cancelling one handle does not cancel the rest of the queue:

```ts
const h1 = agent.send("Build the feature.");
const h2 = agent.send("Make the button blue.");
const h3 = agent.send("Also add a sidebar.");

h1.cancel("stop the current work");

// h2 and h3 remain scheduled.
```

The cancellation result depends on whether the handle has committed its user
message, which happens when its provider request is made:

- Cancelling a queued send removes it from the queue immediately. Its `final`
  rejects with `AxleAgentAbortError`, and no user turn is appended.
- Cancelling the running handle before its provider request — during MCP
  resolution, memory recall, or automatic compaction — also rejects without
  appending a user turn.
- Cancelling after the provider request aborts the active work. The committed
  user message remains in history, and its agent turn is marked cancelled.

Setup failures follow the same rule: if MCP resolution or memory recall
throws, the send rejects with history untouched, so retrying the same message
cannot duplicate its user turn.

To cancel a group, give every operation the same external signal:

```ts
const controller = new AbortController();

const h1 = agent.send("Build the feature.", { signal: controller.signal });
const h2 = agent.send("Make the button blue.", { signal: controller.signal });

controller.abort("cancel the run");
```

Use cancellation, not `stop()`, when the active provider request or tool work
must stop immediately.

### Low-level `stream()` boundary callback

`StreamHandle` now exposes an awaited `onToolBatchComplete` callback. Agent
uses it internally for `stop()`, but direct `stream()` consumers can use the
same complete-batch boundary:

```ts
const handle = stream({
  provider,
  model,
  messages,
  tools,
});

handle.onToolBatchComplete(async (toolResultsMessage) => {
  await persist(toolResultsMessage);
  return shouldHandoff() ? "finish" : "continue";
});

const result = await handle.final;
```

Returning `"finish"` resolves the stream successfully after the tool results
are committed, without starting another provider request. Returning
`"continue"` resumes the normal tool loop. The callback receives one
`AxleToolCallMessage` containing the completed batch and is not a synthetic
stream event.

Wrappers or mocks that implement the `StreamHandle` interface must add
`onToolBatchComplete(callback)`.

## Compaction

Compaction remains experimental in 0.28.0.

### Replace `onCompaction` with `setCompaction`

The callback is now part of a configuration object so its implementation and
automatic timing are configured together:

```ts
// Before
agent.onCompaction(async ({ messages }, { usage, signal }) => {
  if (usage.total < 100_000) return null;
  return summarize(messages, signal);
});

// After
agent.setCompaction({
  compact: async ({ messages }, { usage, signal, trigger }) => {
    if (trigger !== "manual" && usage.total < 100_000) return null;
    return summarize(messages, signal);
  },
  triggers: {
    beforeTurn: true,
  },
});
```

Calling `setCompaction()` again replaces the complete configuration. Omitting
`triggers` preserves the old manual-only behavior:

```ts
agent.setCompaction({ compact });
const record = await agent.compact();
```

`agent.compact()` remains queued behind in-flight work and resolves to a
`CompactionRecord` when messages are replaced or `null` when no callback is
configured or the callback declines.

### Manual compaction cancellation now rejects

In 0.27.1, cancelling `agent.compact({ signal })` resolved `null`, leaving
`null` ambiguous between "declined" and "cancelled". In 0.28.0, cancellation
follows the same contract as `send()`, `stream()`, and
`generate()`: the promise rejects with an `AxleAgentAbortError` (its `name` is
`"AbortError"`), whether the abort lands while the compaction is queued or
while the callback is running. `null` now strictly means no compaction
happened by choice.

```ts
try {
  const record = await agent.compact({ signal });
  // record: CompactionRecord | null (declined or not configured)
} catch (error) {
  if ((error as Error).name !== "AbortError") throw error;
  // cancelled — nothing was changed
}
```

Automatic `beforeTurn`/`afterTurn` compaction is unaffected: it runs inside a
`send()`, so aborting that handle's signal follows the turn's own
cancellation semantics rather than producing a compaction error.

### The callback now receives its trigger

`CompactionCallback` receives a new `trigger` field:

```ts
type CompactionTrigger = "manual" | "beforeTurn" | "afterTurn";

type CompactionCallback = (
  state: { messages: AxleMessage[] },
  context: {
    usage: ContextUsage;
    signal?: AbortSignal;
    trigger: CompactionTrigger;
    lastCompaction?: CompactionRecord;
  },
) => MaybePromise<AxleMessage[] | null>;
```

`lastCompaction` is the receipt of the most recent applied compaction, when
one exists. Its `messageCount` marks how many leading messages of
`state.messages` are carried-over compacted content rather than live
conversation, so callbacks can treat an earlier summary differently from
genuine user messages. `CompactionRecord` gains the same optional
`messageCount` field; records restored from older sessions may lack it.

Callbacks may ignore `trigger` when the same policy should apply everywhere.
Use it when manual compaction should bypass an automatic threshold:

```ts
const compact: CompactionCallback = async ({ messages }, { usage, signal, trigger }) => {
  if (trigger !== "manual" && usage.total < 100_000) return null;
  return summarize(messages, signal);
};
```

Returning `null` leaves active history unchanged. Returning messages replaces
the complete active conversation after structural validation.

### Automatic turn triggers

Configure either or both automatic boundaries:

```ts
agent.setCompaction({
  compact,
  triggers: {
    beforeTurn: true,
    afterTurn: true,
  },
});
```

- `beforeTurn` runs before the next `send()` commits its user message. If
  compaction applies, the new user message is appended to the compacted
  history.
- `afterTurn` runs after a successful turn is committed and before that
  handle's `final` resolves.
- Enabling both invokes the same callback at both boundaries. Return `null`
  whenever no compaction is needed.

Automatic callbacks are awaited and are part of the corresponding handle's
lifecycle. Compaction events and history updates therefore complete before the
handle resolves. An automatic callback error rejects that handle; return
`null` when the callback intentionally declines compaction.

### Compaction callbacks hold the scheduler

Like tool callbacks, the compaction callback runs while the agent's scheduler
is held. Do not await scheduled Agent work (`send()`, `compact()`,
`snapshot()`) from inside it — the nested work queues behind the current
operation, so the await deadlocks:

```ts
agent.setCompaction({
  compact: async () => {
    await agent.send("nested").final; // deadlocks
    return null;
  },
});
```

Fire-and-forget scheduling from inside the callback is safe, and work
scheduled concurrently by other code while a compaction callback is running
queues normally.

### Built-in `PromptCompactor`

Axle now ships a default implementation for prompt-based summarization:

```ts
import { PromptCompactor } from "@fifthrevision/axle";

const compactor = new PromptCompactor({
  provider,
  model,
  prompt:
    "Create a continuation summary. Preserve decisions, constraints, completed work, and open tasks.",
  thresholdTokens: 100_000,
  targetTokens: 20_000,
  recentUserMessages: 10,
});

agent.setCompaction({
  compact: compactor.compact,
  triggers: {
    beforeTurn: true,
  },
});
```

`PromptCompactor`:

- Declines automatic triggers below `thresholdTokens`.
- Runs when manually invoked even below the threshold.
- Produces one user message containing a model-written summary.
- Appends recent user messages in chronological, oldest-to-newest order.
- Keeps 10 recent user messages by default.
- Treats `targetTokens` as the approximate budget for the complete compacted
  message, including the recent-message appendix.
- Drops older recent messages first when the appendix must shrink.
- Excludes messages carried over from the previous compaction (via
  `lastCompaction.messageCount`), so repeated compactions never re-collect an
  earlier summary as a recent user message.

`compactor.compact` is bound and can be passed directly to `setCompaction`.
Generation failures propagate as compaction errors rather than silently
rewriting history.

### History and UI semantics are unchanged

The callback's returned messages become `history.messages`, while raw messages
remain in `history.archive`. Each applied compaction adds a
`{ id, at, messageCount }` receipt
to `history.compactions`.

Compaction continues to emit `compaction:start` and `compaction:end` events and
appears in `history.turns` as an agent turn containing one `compaction` part.
Skipped compactions leave no compaction turn.

## Upgrade Checklist

1. Replace every `agent.onCompaction(callback)` with
   `agent.setCompaction({ compact: callback })`.
2. Add `trigger` handling to compaction callbacks that should distinguish
   manual and automatic policy.
3. Choose `beforeTurn`, `afterTurn`, both, or no automatic compaction trigger.
4. Consider replacing custom prompt summarization with `PromptCompactor`.
5. Use `agent.stop()` + `agent.send()` for follow-ups that should take over
   at the next complete model/tool boundary; add `agent.clear()` in between
   when queued work should be dropped too.
6. Keep results associated with their handles; a stopped handle settles at
   the boundary and does not absorb the follow-up's result.
7. Audit cancellation assumptions: cancelling one handle does not cancel
   queued work owned by other handles; `agent.clear()` drops all queued
   work at once.
8. Handle rejection from cancelled `agent.compact({ signal })` calls; a
   cancelled compaction no longer resolves `null`.
9. Add `onToolBatchComplete` to any custom `StreamHandle` wrappers or mocks.
