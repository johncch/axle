# Migrating to Axle 0.33.0

0.33.0 removes the model registry. Model IDs are plain strings that the
application owns, and Axle no longer ships a catalog of models or their
limits.

The Axle CLI is a separate product; its changes are recorded in
[packages/axle-cli/CHANGELOG.md](../packages/axle-cli/CHANGELOG.md).

---

## Breaking changes

### `@fifthrevision/axle/models` is removed

The `./models` entry point and its exports `Models`, `ModelInfo`, and
`ModelMetadata` no longer exist. Replace each constant with the model ID
string:

```ts
// 0.32
import { Models } from "@fifthrevision/axle/models";

const model = Models.OpenAI.GPT_5_5;

// 0.33
const model = "openai/gpt-5.5";
```

First-party providers still accept both the publisher-qualified form
(`"openai/gpt-5.5"`, `"anthropic/claude-sonnet-5"`, `"google/gemini-3.5-flash"`)
and the bare provider ID (`"gpt-5.5"`).

`ModelInfo` has no replacement. An application that needs a context window or
an output ceiling keeps its own table or asks the provider's models API.

The registry only ever held one wire ID per model, and a model hosted by
several vendors has a different ID on each (DeepSeek's own API, OpenRouter,
and Together name the same model three ways), so the constants could not be
used portably with `chatCompletions()`.

### OpenRouter model IDs are sent unchanged

`chatCompletions()` pointed at OpenRouter used to rewrite a registry identity
to OpenRouter's slug. It no longer rewrites anything; pass the slug OpenRouter
lists:

| 0.32 accepted        | 0.33 requires        |
| -------------------- | -------------------- |
| `zai/glm-5.3`        | `z-ai/glm-5.3`       |
| `minimax/MiniMax-M3` | `minimax/minimax-m3` |

IDs that were already OpenRouter slugs are unaffected.

### `temperature`, `topP`, and `stop` are removed

The three request options are gone from `AxleModelRequestOptions`, and so
from `generate()`, `stream()`, `Agent`, `agent.send()`, and an agent
definition's `request` block. The newest Anthropic and OpenAI models reject
sampling parameters, and the OpenAI provider never supported `stop`, so none
of the three was portable.

Send them through `providerOptions`, which is applied to the request last,
using the provider's own field name:

| Removed option | Anthropic        | OpenAI        | Gemini          | Chat Completions |
| -------------- | ---------------- | ------------- | --------------- | ---------------- |
| `temperature`  | `temperature`    | `temperature` | `temperature`   | `temperature`    |
| `topP`         | `top_p`          | `top_p`       | `topP`          | `top_p`          |
| `stop`         | `stop_sequences` | not supported | `stopSequences` | `stop`           |

```ts
// 0.32
await generate({ provider, model, messages, temperature: 0.2 });

// 0.33
await generate({ provider, model, messages, providerOptions: { temperature: 0.2 } });
```

`stop_sequences` and `stopSequences` take an array; 0.32 accepted a single
string and wrapped it.

### Provider tool parts have one shape on every provider

A `provider-tool` part held `input` and `output` as whatever the provider
sent, and `name` was the provider's own (`web_search` on Anthropic,
`web_search_call` on OpenAI). The fields a UI reads are now the same on every
provider, and the provider's own objects sit in `continuity`:

```ts
// 0.32
{ type: "provider-tool", id, name, input?: unknown, output?: unknown }

// 0.33
{
  type: "provider-tool",
  id,
  name,          // "web_search", "web_fetch", "code_execution", "file_search"
  input?,        // what the tool was asked to do
  result?,       // { type: "success" } | { type: "error", error: { type, message } }
  continuity?,   // the provider's objects, sent back to that provider only
}
```

`input` is one of:

```ts
{ type: "search", queries: string[] }
{ type: "open", url: string }
{ type: "find", url: string, pattern: string }
{ type: "code", code: string }
```

It is absent for a tool Axle has no shape for. `result` is absent while the
tool has not run in that message.

`continuity` is tagged by provider and typed with that provider's SDK types:

```ts
{ provider: "anthropic", call, result? }  // the server_tool_use block and its result block
{ provider: "openai", item }              // the web search, file search, or code interpreter item
```

What 0.32 exposed as `output` is now inside it: on Anthropic the search
results are `continuity.result.content`, and on OpenAI the item is
`continuity.item`. Axle sends these back unchanged, so result blocks from
other Anthropic-run tools (web fetch, code execution) are kept instead of
dropped, and a nested call keeps its `caller`.

A provider tool call goes back only to the provider that made it. A part with
another provider's `continuity`, or none, is left out of the request; 0.32
sent it across. A conversation stored by 0.32 has no `continuity` on these
parts, so its provider tool calls are left out as well.

### Assistant messages can hold a `provider-tool-result` part

The assistant content union has a new member, `ContentPartProviderToolResult`:

```ts
{ type: "provider-tool-result", id, name, result, continuity? }
```

It holds the result of a provider tool call that an earlier assistant message
made. Code that switches exhaustively over assistant content parts needs a
case for it. Only Anthropic produces it, and only when Claude calls an
Anthropic-run tool and one of your tools in the same response: Anthropic then
runs its tool after your tool results come back, and the result opens the
next response.

```ts
// assistant, first step: the search has no result yet
{ type: "provider-tool", id: "srvtoolu_1", name: "web_search",
  input: { type: "search", queries: ["..."] }, continuity: { provider: "anthropic", call } }
{ type: "tool-call", id: "toolu_1", name: "get_build_number", parameters: {} }

// assistant, next step
{ type: "provider-tool-result", id: "srvtoolu_1", name: "web_search",
  result: { type: "success" }, continuity: { provider: "anthropic", result } }
{ type: "text", text: "..." }
```

0.32 dropped that result. `provider-tool:complete` never fired for the call,
and Anthropic rejected every later request in the conversation with
"`web_search` tool use ... was found without a corresponding
`web_search_tool_result` block". The event now fires in the step the result
arrives in, with the id of the original call.

A provider tool that runs on its own keeps its call and result together in
one `provider-tool` part.

### Provider tool events carry Axle's shapes

| Event                    | 0.32                   | 0.33                             |
| ------------------------ | ---------------------- | -------------------------------- |
| `provider-tool:start`    | `id`, `name`           | Unchanged; `name` is Axle's name |
| `provider-tool:input`    | Did not exist          | `id`, `name`, `input`            |
| `provider-tool:complete` | `id`, `name`, `output` | `id`, `name`                     |
| `provider-tool:error`    | Did not exist          | `id`, `name`, `error`            |

`provider-tool:input` fires when the provider says what the tool was asked to
do: before the search runs on Anthropic, and together with the result on
OpenAI. The turn stream has a matching new event, `action:input`, which fills
`detail.input` on the provider-tool action.

`provider-tool:error` replaces `provider-tool:complete` when the provider
reports that its tool failed, and the turn's action settles as `error`. 0.32
reported such a call as a success. On Anthropic a failure is a result block
that carries an `error_code` (for example a search past `max_uses`), and that
code is the `error.type`. On OpenAI it is a tool item whose `status` is
`failed`. A `stream()` consumer that waits for `provider-tool:complete` to
close a provider tool needs to handle `provider-tool:error` as well.

`output` is gone from `provider-tool:complete`, and a successful provider-tool
action no longer has `content`. Read the provider's objects from the part's
`continuity` on the finished message. Code that switches exhaustively over
`StreamEvent` or `TurnEvent` needs cases for the new members.

### A refusal is its own failure kind

When a provider declines a request or blocks its output, `generate()`,
`stream().final`, and `agent.send().final` now resolve `ok: false` with a new
`AxleFailure` member:

```ts
{ kind: "refusal", message: string, text?: string, category?: string }
```

`text` is the refusal text or explanation the provider gave, and `category`
is the provider's own name for the reason. Either can be absent.

| Provider signal                                           | 0.32                                                        | 0.33 `refusal`                              |
| --------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------- |
| Anthropic `stop_reason: "refusal"`                        | `ok: true`, `finishReason: "error"`, `stop_details` dropped | `category`, and `text` from the explanation |
| OpenAI `refusal` content part                             | `ok: true`, `finishReason: "stop"`, empty content           | `text`                                      |
| OpenAI `response.incomplete` with `content_filter`        | `ok: false`, `kind: "model"`, type `IncompleteStream`       | `category: "content_filter"`                |
| Chat Completions `refusal`                                | `ok: true`, `finishReason: "stop"`, empty content           | `text`                                      |
| Chat Completions `finish_reason: "content_filter"`        | `ok: true`, `finishReason: "error"`                         | `category: "content_filter"`                |
| Gemini `promptFeedback.blockReason`                       | `ok: false`, `kind: "model"`, type `Blocked`                | `category`, and `text` from the message     |
| Gemini finish reason `SAFETY`, `PROHIBITED_CONTENT`, etc. | `ok: false`, `kind: "model"`, type `FinishReasonError`      | `category`, and `text` from `finishMessage` |

What to change:

- Code that switches exhaustively over `error.kind` needs a `"refusal"` case.
- Code that detected an Anthropic refusal by `finishReason === "error"` on an
  `ok: true` result, or a Gemini block by `error.error.error.type`, reads
  `error.kind === "refusal"` instead. The Gemini failures no longer carry
  `raw`, so `safetyRatings` are not reachable from the result.
- An `Instruct` call that is refused returns the refusal. On OpenAI and Chat
  Completions it used to return a `parse` failure.

The refused step is not stored: `messages` holds only the steps that
completed before it, `step:complete` does not fire, and the stream's last
event is `error` with the same failure. On a turn it is
`error: { type: "refusal", message }`. After a refused `agent.send()` the
agent's history ends with the user message; 0.32 also stored the empty or
partial assistant message wherever it returned `ok: true`.

A refusal the model writes as ordinary text is not marked by any provider and
is still a normal `ok: true` answer.

### Failures are flat, and a rejected key is `type: "authentication"`

`AxleFailure`, the `error` on an `ok: false` result, no longer nests a
second object under `error`. The `model` member carries the fields directly,
`ModelError` is removed, and the never-produced `tool` member is gone:

```ts
// 0.32
| { kind: "model"; error: ModelError; message: string }   // ModelError = { type: "error", error: { type, message }, usage?, raw? }
| { kind: "tool"; error: { name: string; message: string }; message: string }
| { kind: "parse"; error: unknown; message: string }

// 0.33
| { kind: "model"; type: string; message: string; status?: number; usage?: Stats; raw?: unknown }
| { kind: "parse"; message: string; cause: unknown }
```

| 0.32                           | 0.33                                        |
| ------------------------------ | ------------------------------------------- |
| `error.error.error.type`       | `error.type`                                |
| `error.error.error.message`    | `error.message` (already there, same value) |
| `error.error.raw`              | `error.raw`                                 |
| `error.error.usage`            | `error.usage`                               |
| `error.error.raw.status`       | `error.status`                              |
| `error.error.type` (`"error"`) | Removed; `kind` is the discriminator        |
| parse `error.error`            | `error.cause`                               |

Two new things on a `model` failure:

- `type` is `"authentication"` when the provider rejected the API key or
  token: HTTP 401 on Anthropic, OpenAI, and Chat Completions, or Gemini's 400
  with reason `API_KEY_INVALID`. 0.32 reported these as `Error`, `ApiError`,
  or `"401"` depending on the provider, and a consumer had to read
  `raw.status` and Gemini's message string itself. Every other failure keeps
  the type it had.
- `status` is the HTTP status when the failure was an HTTP response, on every
  provider. It is absent for a transport failure or a mid-stream error.

```ts
// 0.32
if (!result.ok && result.error.kind === "model") {
  const raw = result.error.error.raw;
  if (raw?.status === 401 || (raw?.status === 400 && raw?.message?.includes("API_KEY_INVALID"))) {
    // bad key
  }
}

// 0.33
if (!result.ok && result.error.kind === "model" && result.error.type === "authentication") {
  // bad key
}
```

Nothing produced a `tool` failure: a tool that throws is returned to the
model as an error result, and a fatal tool error throws. A `switch` over
`kind` that has a `"tool"` case no longer compiles.

### `AxleStopReason.Error` and `AxleStopReason.Custom` are removed

`finishReason` on an assistant message is now one of `stop`, `length`,
`function_call`, or `cancelled`. Nothing produced `custom`, and the two
cases that produced `error` are now failures:

| Case                                                                | 0.32                                              | 0.33                                                   |
| ------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------ |
| An Anthropic `stop_reason` Axle does not know                       | `ok: true`, `finishReason: "error"`, content kept | `ok: false`, `kind: "model"`, type `FinishReasonError` |
| An OpenRouter `finish_reason: "error"` with no `error` on the chunk | `ok: true`, `finishReason: "error"`, content kept | `ok: false`, `kind: "model"`, type `FinishReasonError` |

Code that compares against either member no longer compiles; a check for
`finishReason === "error"` can be replaced by `!result.ok`.

## Behavior changes

### Anthropic `pause_turn` responses continue automatically

Anthropic can end a response with `stop_reason: "pause_turn"` while its own
tool loop still has work to do. 0.32 returned that partial response as a
finished answer with `finishReason: "error"`. The Anthropic provider now
sends the follow-up request itself until the turn finishes, for `generate()`,
`stream()`, and `Agent` alike.

The continued turn is one step: one `step:start` and `step:complete`, one
assistant message, and usage summed over every request. It counts once toward
`maxSteps` however many requests it took, and `maxContextTokens` is checked
against the summed usage.

### OpenRouter requests carry the agent's `sessionId`

`stream()`, `generate()`, and `ProviderStreamParams` take an optional
`sessionId`, and `Agent` passes its own on every request. The Chat
Completions provider sends it as OpenRouter's `session_id` when the vendor is
`openrouter`, so a conversation sticks to one upstream provider from its
first request and its requests are grouped in the OpenRouter dashboard. Other
providers and vendors ignore the field.

A caller that already sets `providerOptions: { session_id }` keeps that
value, since raw provider options override Axle's mappings. A host that
passes its own `sessionId` to `Agent` should expect OpenRouter to see it.

### Anthropic's implicit `max_tokens` defaults to 128,000

When the caller sets no `maxOutputTokens`, the Anthropic provider sent the
model's registry ceiling, else 64,000. It now sends 128,000, or 64,000 for
Haiku 4.5, Opus 4.5, and Sonnet 4.5 (alias and dated IDs).

Every model the registry listed gets the same value as before. A model the
registry did not list now gets 128,000 instead of 64,000; if its real ceiling
is lower, Anthropic rejects the request until you pass `maxOutputTokens`.

### A reply split across text parts is read as one run of text

A provider can return one reply as several adjacent text parts; Anthropic
does so whenever it cites a document, one part per cited span. Axle joined
those parts with a blank line, which broke sentences apart and made
`Instruct` JSON unparseable ("Bad control character in string literal").

Adjacent text parts are now concatenated directly. A blank line is inserted
only where a tool call, thinking part, or file sits between two text parts.
This changes the string `agent.send()` returns as `response`, the text an
`Instruct` parses, the assistant text replayed to OpenAI, and
`PromptCompactor` summaries. The message's `content` parts are unchanged.

### `web_search` resolves to newer provider versions

| Provider  | 0.32                  | 0.33                                                     |
| --------- | --------------------- | -------------------------------------------------------- |
| Anthropic | `web_search_20250305` | `web_search_20260318` with `allowed_callers: ["direct"]` |
| OpenAI    | `web_search_preview`  | `web_search`                                             |

Search behaves as before on both: the same result blocks and items, the same
citations. On Anthropic the newer version would by default run searches from
inside code execution (dynamic filtering); Axle sends
`allowed_callers: ["direct"]` to keep direct searches, and a model without
programmatic tool calling requires that setting. Opt in to dynamic filtering
with `config: { allowed_callers: ["code_execution_20260120"] }`.

`config.type` pins the old version, for example
`config: { type: "web_search_20250305" }`.

### A Gemini search produces a provider-tool part

A Gemini answer that used Google Search carried citations but no sign that a
search ran. It now also holds a `provider-tool` part named `web_search`, with
the queries Gemini ran as its `input`, and `stream()` emits
`provider-tool:start`, `provider-tool:input`, and `provider-tool:complete`
for it.

Gemini reports the queries only in the last chunk of the response, so the
part sits after the answer text and the three events fire together when the
answer ends. The part has no `continuity` and is not sent back.

### OpenAI assistant items are sent back in their original order

The OpenAI provider rebuilt an earlier assistant message as all of its text,
then its reasoning items, then its function calls, then its provider tool
items. OpenAI requires a reasoning item to sit directly before the web search
it led to, so a conversation where the model reasoned between two searches
failed on its next request with "Item ... of type 'web_search_call' was
provided without its required 'reasoning' item".

Items now go back in the order of the message's `content` parts, which is the
order OpenAI returned them. Text separated by a function call, a reasoning
item, or a provider tool item is sent as separate assistant messages instead
of one joined message.

OpenAI's `phase` label on answer text (`commentary` or `final_answer`) is now
kept and sent back, as OpenAI asks. It is stored on the text part as
`providerMetadata: { provider: "openai", phase }`; nothing else about stored
messages changes.

### OpenAI reasoning continuity arrives when the reasoning item completes

The OpenAI provider read a reasoning item's `encrypted_content` when the item
opened. OpenAI documents that value as possibly incomplete, and the completed
item carries a different one. Axle now stores the completed value.

The stored message is the only thing that changes for most callers. A
`stream()` consumer that read `continuity` from the `thinking:start` event on
OpenAI now receives it on `thinking:update`, just before `thinking:end`.

### OpenAI output cut off at `maxOutputTokens` finishes with `length`

OpenAI ends a truncated response with a `response.incomplete` event, which
the provider did not handle. The call failed with
`Stream ended without a completion signal`, and the text produced so far was
lost. It now resolves `ok: true` with `finishReason: "length"` and the partial
content, as the other providers do. A `response.incomplete` with any other
reason is a `model` failure of type `RESPONSES_API_INCOMPLETE` that names the
reason.

### Anthropic `model_context_window_exceeded` finishes with `length`

Anthropic ends a response with this stop reason when the context window
fills before the output cap, and documents the response as valid but
truncated. 0.32 reported it as `finishReason: "error"`; it is now
`finishReason: "length"`, the same as `max_tokens`.
