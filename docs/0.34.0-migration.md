# Migrating to Axle 0.34.0

0.34.0 adds two turn events for queued work and a `pending` turn status,
which breaks code that handles `TurnEvent`, `TurnStatus` or a compaction
part's status exhaustively. `stream()` and `generate()` no longer take a
`registry`, tools no longer receive one, and `agent.system` is read-only.
The Agent gains `onSettled`, `onIdle`, `cancel` and a `skills` registry, and
`Transcript` gains `pending`. `chatCompletions()` gains a default request
timeout and reports a timeout as one. `snapshot()` waits for the Agent to
go idle and no longer takes a place in the queue. Providers now own provider tools:
`configureAxle` and the web search fallback are gone, and a search is
attached to the `chatCompletions()` provider that needs one.

The Axle CLI is a separate product; its changes are recorded in
[packages/axle-cli/CHANGELOG.md](../packages/axle-cli/CHANGELOG.md).

---

## Breaking changes

### `TurnEvent` gains `pending:queued` and `pending:dropped`

The Agent now announces an operation — a `send()` or a manual `compact()` —
when it is accepted, and announces it again if it ends before opening its
turn.

```ts
| { type: "pending:queued"; turn: Turn } // turn.status === "pending"
| { type: "pending:dropped"; id: string; reason: PendingDropReason }
```

A `switch` over `event.type` that ends in an exhaustiveness check, such as
`event satisfies never`, stops compiling until it handles both. A renderer that has
no use for them can ignore them; `Transcript.apply` already folds them.

Two assumptions that used to hold no longer do:

| Before                                                 | 0.34                                                   |
| ------------------------------------------------------ | ------------------------------------------------------ |
| The first event of a send is `turn:user`               | `pending:queued` comes first, inside the `send()` call |
| A send or compact that never starts emits nothing      | It emits `pending:queued`, then `pending:dropped`      |
| The first event of a manual compaction is `turn:start` | `pending:queued` comes first                           |

The second row covers a handle cancelled while queued, `agent.clear()`, a
signal that was already aborted, and a setup failure such as an unreachable
MCP server. No user message is committed in any of them, as before.

### `TurnStatus` and the compaction part's status gain `"pending"`

A pending entry is a preview `Turn` with `status: "pending"`, and a queued
manual compaction previews as an agent turn with one compaction part whose
`status` is `"pending"`. A `switch` over either status that ends in an
exhaustiveness check stops compiling until it handles the new value. A
`pending` turn only ever appears in `transcript.pending`, never in `turns`,
so a renderer that reads `turns` alone can treat the case as unreachable.

### `registry` is gone from `stream()` and `generate()`

`StreamParams.registry` is removed; pass `tools` and `providerTools`. The
loop builds every request from the values it was given and never reads a
registry, so a tool added to a `ToolRegistry` after the call no longer
appears mid-loop. To change tools or the prompt during a loop, return them
from `onToolBatchComplete` (see Additions). Passing `registry` is now a
type error; the `TOOL_OPTIONS_CONFLICT` error no longer exists.

### `ToolContext.registry` is gone

A tool's `execute(input, ctx)` no longer receives `ctx.registry`. Nothing in
Axle read it. A tool that changes the agent it runs under uses that agent
in closure scope: `agent.registry.add(...)`, `agent.skills.add(...)`.

### `ResolvedProviderTool` and `nativeName` are gone

Provider adapters receive `ProviderTool[]` and resolve native names with
their own resolver, as they already did. Only a custom `AIProvider` that
read `nativeName` is affected: call your own resolver instead.

### `configureAxle` and the web search fallback are gone

Web search on a provider without a hosted search used to be a process-wide
setting. It is now a tool attached to the provider that needs it. The design
is in [architecture/provider-tools.md](./architecture/provider-tools.md).

```ts
// 0.33
configureAxle({ webSearchFallback: braveWebSearch({ apiKey: braveKey }) });
const provider = chatCompletions("https://api.together.ai/v1", { apiKey });

// 0.34
const provider = chatCompletions("https://api.together.ai/v1", {
  apiKey,
  webSearch: braveWebSearch({ apiKey: braveKey }),
});
```

The `providerTools: [{ type: "provider", name: "web_search" }]` request is
unchanged.

| Removed                                                                                | Use instead                                                    |
| -------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `configureAxle`, `AxleConfiguration`                                                   | `webSearch` on each `chatCompletions()` provider that needs it |
| `WebSearchBackend`, `WebSearchBackendContext`, `WebSearchRequest`, `WebSearchResponse` | `ExecutableTool`                                               |
| Error code `WEB_SEARCH_FALLBACK_NOT_CONFIGURED`                                        | A provider error with no code (see Behavior changes)           |

A search set once for the whole process no longer exists: attach it to every
`chatCompletions()` provider that should have it. Anthropic, OpenAI and
Gemini host their own search and take no `webSearch`.

### `braveWebSearch()` returns a tool, not a backend

`braveWebSearch(options)` now returns an `ExecutableTool` named `web_search`.
Its options are unchanged. Code that called the backend directly changes:

```ts
// 0.33
const { results } = await brave.search({ query }, { signal });

// 0.34
const text = await brave.execute({ query }, { signal, emit: () => {} });
const { results } = JSON.parse(String(text));
```

A custom backend becomes a tool. Where you implemented
`WebSearchBackend.search`, write an `ExecutableTool` whose `execute` returns
the results as a string, and pass it as `webSearch`.

### `AIProvider.resolveProviderToolName` is gone

The loop no longer asks a provider whether it supports a provider tool. A
custom `AIProvider` that implemented `resolveProviderToolName` can delete
it; it receives `providerTools` unchanged, as before. A custom provider that
relied on the fallback to serve `web_search` now lists the tool in
`AIProvider.tools` (see Additions).

### `agent.system` is read-only

`agent.system` is now a getter: the configured system prompt, then the
skills catalog when skills are present. Code that assigned
`agent.system = ...` stops compiling; the configured prompt is set at
construction.

## Additions

### `agent.skills`

A `SkillRegistry` with `add`, `remove`, `has`, `get`, `list` and `size`.
The Agent owns `view-skill` and rebuilds it on every change; removing the
last skill removes the catalog and the tool. A change is visible on the
next provider request, including the next step of a turn already running.
`config.skills` seeds it; `SkillRegistry` is exported for direct use with
a `ToolRegistry`.

### `onToolBatchComplete` may return new inputs

Besides `"continue"` and `"finish"`, the callback may return
`{ system?, tools?, providerTools? }`: the loop continues with those inputs
replacing the current ones, exactly as the initial call set them. The type
is `ToolBatchDecision`.

### `Transcript.pending`

`transcript.pending` lists the operations the Agent has accepted but not
started, as `Turn`s with `status: "pending"`: the user turn a send will
commit, or an agent turn with a `pending` compaction part for a manual
compaction. Each carries the `id` the real turn will have, and leaves when
that turn opens or the operation is dropped, so `[...turns, ...pending]`
renders with one component keyed by id. Pending turns are never part of
`turns`: saving `turns` does not save them and a `Transcript` restored from
saved turns has none.

### `new Transcript(turns, pending)`

The constructor takes pending turns as an optional second list, to mirror
a live transcript for a client that receives the server's `turns`,
`pending` and stream position in one read. It discards a pending turn whose id is already in `turns`. This
does not change what is saved: persist `turns` only.

### `agent.onSettled(callback)`

Fires once after each send or manual compaction that ran, however it
ended — after its `turn:end` when it opened a turn, and before the
operation's handle settles. The callback receives the value `snapshot()`
returns and a `SettledOperation` with the operation's `kind`, the `id` its
`pending:queued` turn carried, and a `result` that is exactly what the
handle settles with, as a `PromiseSettledResult`. Use it to save as each operation finishes without
waiting for the queue to empty the way `snapshot()` does, and to react to the
outcome without also awaiting the handle:

```ts
agent.onSettled(async (session, operation) => {
  await save(session, [...transcript.turns]);
  if (operation.result.status === "rejected") report(operation.result.reason);
});
```

The Agent awaits the callback: return a promise and neither the handle nor
the next queued operation proceeds until it resolves. Callbacks run
together. `cancel()` and `stop()` return `false` while they run. A callback
that throws or rejects does not affect the operation: the error is recorded
on the trace and the handle settles with its real result. Do not await
`send()`, `compact()` or `snapshot()` on the same agent from inside the
callback; it holds the queue they wait for.

`SettledOperation` and `SettledCallback` are exported.

### `agent.onIdle(callback)`

Fires each time the Agent goes from busy to idle: an operation finished
and nothing is queued behind it. It comes after the
last operation's `onSettled` callbacks have settled, and it also fires when
`clear()` empties the queue while they run. Use it to close whatever the
host opened when work began:

```ts
agent.onIdle(() => notifyClients({ type: "run:stop" }));
```

The callback takes no arguments and is not awaited; a `send()` from inside
it starts at once. A callback that throws is recorded on the trace.
`IdleCallback` is exported.

### `agent.cancel(reason?)`

Cancels the active operation immediately, as that handle's own `cancel()`
would, and returns `false` when nothing is running. Queued operations are
unaffected. `stop()` remains the gentle form and `clear()` still drops only
what is queued.

### `webSearch` on `chatCompletions()`

`ChatCompletionsOptions.webSearch` takes an `ExecutableTool`. When a request
carries the `web_search` provider tool, the provider sends the attached tool
to the model as a function tool and the loop runs it as an ordinary tool
call.

### `AIProvider.tools`

An optional `ExecutableTool[]`: executable tools the provider brings. When
the model calls a tool whose name is not among the caller's tools, the loop
runs the provider's tool of that name. `chatCompletions()` uses it for an
attached `webSearch`.

## Behavior changes

### `chatCompletions()` fails on a provider tool it cannot serve

A `chatCompletions()` provider with no vendor that hosts tools used to log a
warning and drop every provider tool; a Together provider dropped them
without a warning. Both now fail the request before it is sent:

| Request                                     | 0.33                                              | 0.34                                       |
| ------------------------------------------- | ------------------------------------------------- | ------------------------------------------ |
| `web_search`, no fallback configured        | Rejects with `WEB_SEARCH_FALLBACK_NOT_CONFIGURED` | Fails: `ok: false`, message names the tool |
| `code_execution` or any other provider tool | Dropped, the request is sent without it           | Fails: `ok: false`, message names the tool |

The 0.33 `web_search` error rejected the handle. The 0.34 error is a
provider error, like any other request a provider cannot build: the handle
resolves with `ok: false`, `error.kind` is `"model"` and `error.message` is
`ChatCompletions does not support provider tool: web_search`. There is no
error code.
OpenRouter is unchanged: it hosts `web_search` and still warns and skips a
name it does not map.

### An attached search is used on OpenRouter

Hosted search used to win wherever it existed, so a fallback was ignored on
OpenRouter. A `webSearch` attached to an OpenRouter provider now runs in
place of `openrouter:web_search`. Do not attach one if you want OpenRouter's.

### `web_search.config` is ignored without a warning

`config` on the `web_search` provider tool never reached the fallback, and
a warning said so. It still does not reach an attached tool, and there is no
warning.

### `snapshot()` waits for idle, not for its place in the queue

`snapshot()` used to be queued like a send and resolved when its turn in
the queue came. It now resolves at once when the Agent is idle, and
otherwise when the Agent next goes idle. `send(); send(); await snapshot()`
is unchanged. Two cases differ:

```ts
agent.send("a");
const session = agent.snapshot();
agent.send("b");
await session; // before: holds "a". Now: holds "a" and "b".
```

`clear()` no longer cancels a waiting `snapshot()`, so it no longer rejects
with `AxleAgentAbortError`. To save after each operation, use `onSettled`.

### A user turn is stamped when `send()` is called

`send()` now builds the user message and its turn up front, so the queued
preview (status `"pending"`) and the committed turn (status `"complete"`)
share their id, parts and timing. The turn's `timing` is therefore the
moment of the `send()` call, not the moment the turn committed. For a send
that waited in the queue the two differ by the wait.

### A cancelled turn is always recorded as `cancelled`

When a send was cancelled and the provider rethrew something that did not
look like an abort (a custom `reason` string, for one), the handle rejected
as an abort but the agent turn ended with `status: "error"`. The turn status
now follows the abort signal, so the two agree.

### `chatCompletions()` requests time out after ten minutes

A `chatCompletions()` request with no `timeoutMs` used to wait indefinitely
for the endpoint to start responding. Each attempt now gives up after ten
minutes, the default the OpenAI and Anthropic SDKs already apply. The timer
covers the wait for the response to start, not the stream that follows, and
it restarts on every retry, so with the default `maxRetries: 2` an endpoint
that never answers fails after about thirty minutes.

Pass `timeoutMs` to choose a different limit:

```ts
const provider = chatCompletions("http://localhost:11434/v1", {
  timeoutMs: 30 * 60_000,
});
```

`anthropic()`, `openai()`, and `gemini()` are unchanged: without `timeoutMs`
they use whatever their SDK does.

### A `chatCompletions()` timeout fails as `TimeoutError`

When an attempt timed out and no retries were left, the failure carried
`type: "AbortError"` and the message `Request aborted`, the same as a
cancellation. It now carries the timer's own error:

| Field     | 0.33                | 0.34                              |
| --------- | ------------------- | --------------------------------- |
| `type`    | `"AbortError"`      | `"TimeoutError"`                  |
| `message` | `"Request aborted"` | `"Request timed out after <n>ms"` |

Code that matched `AbortError` to detect a `chatCompletions()` timeout
should match `TimeoutError`. Aborting through the caller's own signal is
unchanged.
