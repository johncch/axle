# Migrating to Axle 0.34.0

0.34.0 adds two turn events for queued work, which breaks code that handles
`TurnEvent` exhaustively. The Agent gains `onSettled` and `cancel`, and
`Transcript` gains `pending`. `chatCompletions()` gains a default request
timeout and reports a timeout as one.

The Axle CLI is a separate product; its changes are recorded in
[packages/axle-cli/CHANGELOG.md](../packages/axle-cli/CHANGELOG.md).

---

## Breaking changes

### `TurnEvent` gains `pending:queued` and `pending:dropped`

The Agent now announces an operation — a `send()` or a manual `compact()` —
when it is accepted, and announces it again if it ends before opening its
turn.

```ts
| { type: "pending:queued"; entry: PendingEntry }
| { type: "pending:dropped"; id: string; reason: PendingDropReason }
```

A `switch` over `event.type` that ends in an exhaustiveness check, such as
`event satisfies never`, stops compiling until it handles both. A renderer that has
no use for them can ignore them; `Transcript.apply` already folds them.

Two assumptions that used to hold no longer do:

| Before                                                 | 0.34                                                   |
| ------------------------------------------------------ | ------------------------------------------------------ |
| The first event of a send is `turn:user`               | `pending:queued` comes first, inside the `send()` call |
| A send or compact that never starts emits nothing      | It emits `pending:queued`, then `pending:dropped`      |
| The first event of a manual compaction is `turn:start` | `pending:queued` comes first                           |

The second row covers a handle cancelled while queued, `agent.clear()`, a
signal that was already aborted, and a setup failure such as an unreachable
MCP server. No user message is committed in any of them, as before.

## Additions

### `Transcript.pending`

`transcript.pending` lists the operations the Agent has accepted but not
started. Each entry has the `id` of the turn it will open and a `kind`:
`"send"` carries a preview user `turn`, `"compaction"` carries nothing more.
An entry leaves when a turn with its id opens or when it is dropped. Pending
entries are never part of `turns`: saving `turns` does not save them and a
restored `Transcript` has none.

### `agent.onSettled(callback)`

Fires once after each send or manual compaction that opened a turn, after
that turn's `turn:end` and before the operation's handle settles, with the
value `snapshot()` returns. Use it to save as each operation finishes
without waiting behind the queue the way `snapshot()` does:

```ts
agent.onSettled((session) => save(session, [...transcript.turns]));
```

A callback that throws does not affect the operation: the error is recorded
on the trace and the handle settles with its real result.

### `agent.cancel(reason?)`

Cancels the active operation immediately, as that handle's own `cancel()`
would, and returns `false` when nothing is running. Queued operations are
unaffected. `stop()` remains the gentle form and `clear()` still drops only
what is queued.

## Behavior changes

### A user turn is stamped when `send()` is called

`send()` now builds the user message and its turn up front, so the queued
preview and the committed turn are the same object. The turn's `timing` is
therefore the moment of the `send()` call, not the moment the turn
committed. For a send that waited in the queue the two differ by the wait.

### A cancelled turn is always recorded as `cancelled`

When a send was cancelled and the provider rethrew something that did not
look like an abort (a custom `reason` string, for one), the handle rejected
as an abort but the agent turn ended with `status: "error"`. The turn status
now follows the abort signal, so the two agree.

### `chatCompletions()` requests time out after ten minutes

A `chatCompletions()` request with no `timeoutMs` used to wait indefinitely
for the endpoint to start responding. Each attempt now gives up after ten
minutes, the default the OpenAI and Anthropic SDKs already apply. The timer
covers the wait for the response to start, not the stream that follows, and
it restarts on every retry, so with the default `maxRetries: 2` an endpoint
that never answers fails after about thirty minutes.

Pass `timeoutMs` to choose a different limit:

```ts
const provider = chatCompletions("http://localhost:11434/v1", {
  timeoutMs: 30 * 60_000,
});
```

`anthropic()`, `openai()`, and `gemini()` are unchanged: without `timeoutMs`
they use whatever their SDK does.

### A `chatCompletions()` timeout fails as `TimeoutError`

When an attempt timed out and no retries were left, the failure carried
`type: "AbortError"` and the message `Request aborted`, the same as a
cancellation. It now carries the timer's own error:

| Field     | 0.33                | 0.34                              |
| --------- | ------------------- | --------------------------------- |
| `type`    | `"AbortError"`      | `"TimeoutError"`                  |
| `message` | `"Request aborted"` | `"Request timed out after <n>ms"` |

Code that matched `AbortError` to detect a `chatCompletions()` timeout
should match `TimeoutError`. Aborting through the caller's own signal is
unchanged.
